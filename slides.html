Phần 1 - Đặt Vấn Đề (Problem Statement)

Nỗi Đau Tích Hợp Khi Không Có API Contract

Làm thế nào để đội ngũ bên ngoài (Frontend, Mobile, Third-party) tích hợp Cart API mà không cần phải mở từng dòng mã nguồn Backend ra đọc?

1. Lệch đặc tả (Schema Drift)

Viết OpenAPI YAML thủ công tách rời code: Khi backend đổi tên trường hoặc sửa kiểu dữ liệu, tài liệu không được cập nhật kịp thời, dẫn tới việc Client gửi request bị lỗi.

2. Lỗi thư viện lọt ra ngoài

Mỗi thư viện (Express body-parser, Database ORM, Validator) tự ném ra một định dạng JSON riêng biệt, khiến Client không thể viết hàm bắt lỗi và rẽ nhánh tập trung.

3. Mất dấu vết (No Traceability)

Khi người dùng báo lỗi 500 ở môi trường thật, lập trình viên không biết tìm request đó ở đâu giữa hàng triệu dòng log vì thiếu mã định danh request_id xuyên suốt.

Phần 2 - Kiến Trúc Giải Pháp (Solution Architecture)

Code-First & Single Source of Truth

Lựa chọn Code-First với TypeScript + Zod đảm bảo Schema kiểm tra dữ liệu và Schema render tài liệu là MỘT nguồn duy nhất.

Lý do chọn Code-First (Zod + TypeScript)
  • [x] Single Source of Truth: Định nghĩa Zod Schema 1 nơi, dùng cho cả Runtime Validation lẫn sinh OpenAPI 3.1.
  • [x] Type-Safe tuyệt đối: TypeScript tự động suy diễn kiểu dữ liệu qua z.infer cho tầng Service và Controller.
  • [x] Boundary Validation: Chặn đứng dữ liệu rác, quantity ngoài [1..10], thuộc tính lạ (.strict()) ngay tại cổng.
  • [x] Phòng chống 4 cạm bẫy Slide 21: Chuẩn hóa Error Contract, không lọt lỗi thư viện, không tin giá gửi từ client.

Phần 2 - Vòng Đời Request (Request Lifecycle)

Luồng Xử Lý Request & Chuẩn Hóa Lỗi

Bảo vệ 3 lớp: Tracing Request ID -> Structured Logging -> Boundary Validation -> Transaction Isolation.

Sơ đồ tuần tự xử lý Request
[1. Client Request] + Header: X-Request-Id (optional)
        │
[2. requestIdMiddleware]
        ├── Có X-Request-Id: Tiếp tục sử dụng
        └── Không có: Tự sinh UUID v4 bằng crypto.randomUUID()
        │
[3. Pino HTTP Logger] Gắn req_id, redact password/token/auth
        │
[4. Zod Boundary Validation]
        ├── Thất bại: Chặn NGAY -> 400 VALIDATION_ERROR (Zero DB hit)
        └── Hợp lệ: Chuyển tiếp Controller -> Service
        │
[5. Service Layer + DB Transaction]
        ├── Khóa dòng: SELECT ... FOR UPDATE (Chống Race Condition)
        └── Tính subtotal_cents 100% từ giá trong bảng products
        │
[6. Centralized Error Handler]
        ├── AppError: 400, 404, 409, 422 chuẩn hóa JSON
        └── Error 500: Trả thông báo chung, stack trace lưu log
* Nguyên tắc: Không bao giờ để lỗi CHECK constraint của database văng ra thành lỗi 500.

Phần 5 - Đánh Giá & Kết Luận (Conclusion)

Trade-Offs, Đánh Giá & Hướng Mở Rộng

Các quyết định kỹ thuật đã cân nhắc và những giải pháp cải tiến trong tương lai.

Trade-off Đã Cân Nhắc
1. Code-First so với Contract-First:
- Ưu điểm: Code-First mang lại type-safety tối đa, dev viết nhanh và không bao giờ bị lệch spec.
- Giới hạn: Phụ thuộc hệ sinh thái TypeScript. Nếu microservices đa ngôn ngữ, Contract-First bằng Protobuf/OpenAPI tập trung sẽ phù hợp hơn.
2. Tranh chấp tồn kho (Race Condition):
- Hiện tại: Dùng Row-Level Lock SELECT ... FOR UPDATE trong Postgres Transaction chống bán vượt tồn kho (oversold).
- Giới hạn: Phù hợp quy mô vừa và nhỏ. Khi Flash Sale với hàng vạn request/giây, hàng đợi khóa DB có thể bị nghẽn.
Hướng Phát Triển Mở Rộng
  • - Redis Distributed Lock (Redlock): Khóa tồn kho tại tầng Cache để giảm tải cho DB trong các sự kiện Flash Sale.
  • - OpenTelemetry Integration: Mở rộng từ X-Request-Id sang Distributed Tracing (Jaeger/Zipkin) xuyên suốt các microservices.
  • - Idempotency-Key Header: Chống bấm nút thêm giỏ hàng nhiều lần liên tiếp khi kết nối mạng chập chờn.
